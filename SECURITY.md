# Security Policy

## Reporting a vulnerability

**Please do not open a public issue for a security problem.**

Report it through GitHub's private vulnerability reporting: open the **Security** tab of the
affected repository and choose **Report a vulnerability**. That opens a private advisory
visible only to the maintainers.

If private reporting is not enabled on the repository, open a normal issue saying only that you
have a security report and asking for a private channel — no details.

## What to expect

- **Acknowledgement within 7 days.**
- An assessment of severity and affected versions, and whether a fix is planned.
- Credit in the advisory and release notes, unless you would rather stay anonymous.

This is a small project run by a small team; there is no bug bounty, and response times are
best-effort rather than contractual.

## Scope

Supported: the latest release of each project, and `main`.

Particularly interested in reports about:

- **Sandbox escape** — code in a workflow cell reaching the host beyond its declared permissions.
- **Permission bypass** — a workflow obtaining network or vault access it was not granted.
- **Secret disclosure** — API keys reaching logs, output files, or a container that should not
  see them.
- **Supply chain** — anything that lets a dependency or workflow file execute unexpected code.

Out of scope: findings that need an already-compromised machine, vulnerabilities in third-party
container images we do not build, and reports generated by a scanner without a demonstrated
impact.

## A note on how these tools work

VaultOre executes code from Markdown notes inside containers. A note is therefore executable
content: treat one from an untrusted source with the same care as an untrusted script. Reports
that depend on a user deliberately running a hostile note are still welcome — the sandbox is
meant to contain exactly that — but please say so in the report.
